# 开发记录：问题、方案和取舍

这篇按项目记录开发中遇到的主要问题：现象、原因、试过的方案、最后选了哪个、为什么，以及每一步对召回率、精确率的影响。
规则本身的细节见 [颠球](juggling.md)、[跳绳](jumprope.md)、[运球](dribble.md)；这里重点讲"为什么这样做"。

- **召回** = 人工标的真值里，程序数到的比例（漏数让它变低）；
- **精确率** = 程序数出来的里面，真的比例（多数让它变低）；
- 表里写"A / B"的地方，A 是召回、B 是精确率。

## 1. 准确率是怎么来的

### 1.1 标注

| 项目 | 标什么 | 怎么标 | 对上的容差 |
|---|---|---|---|
| 颠球 | 每次触球的帧号；落地、手接、看不清的另记 | 球的低点和丢失时段逐处画前后几帧的放大图（`tools/label/label_helper.py`），人逐个判断 | ±4 帧（最早 4 段 ±3 帧） |
| 跳绳 | 每次绳子过脚 = 一跳，取腾空最高点的帧号 | 脚部逐帧小图；第 2 批起改用像素运动轨迹图（`tools/label/jumprope_kymo.py`），**和关键点算法完全无关** | ±4 帧，或一跳周期的 20%（慢动作时更宽），取大的 |
| 运球 | 每次球碰地的帧号；每一下的动作 | 逐帧小图（`tools/label/dribble_label.py`），动作看每一下一行的小图和放大图 | ±3 帧 |

计分时：标成"看不清"（`ambiguous`）的附近，程序报不报都不扣分；`ignore` 时段（剪辑切换、球出画面）整段不计；
颠球的"手接、抛"（`nocount`）附近报了触球算误报，并单独统计。

### 1.2 标注本身会错

开发过程中人工标注错过好几次，都是**程序和标注对不上、放大逐帧复查后才发现标注错了**：

- 颠球最早 4 段：球停在脚背上再挑起、贴地的脚触球、球落在脚尖上又弹回大腿，最初都标成了"落地"；
- 颠球第 2 批：两处"手拿着球"标成了触球，是程序判对了；
- 颠球第 4 批：4 处（漏标的脚颠、落地和触球标反）；
- 运球动作：2 下胯下标成了交叉，1 下看不清；
- 运球：一段片尾的真触地漏标（换了检测以后程序数到了，回看确认是真的）。

所以定了两条规矩：每次程序和标注不一致，都把触点前后各 7 帧放大复查，改了的标注在 `note` 里写清楚；
第一次跑之前的标注原样另存（`labels.first_run_snapshot.json`），第一次跑的数字不因为事后改标注而改写。

### 1.3 留出集

规则是手写的，看着哪段视频调，就会在哪段上变好，所以"调参用的视频上 100%"说明不了什么。做法是：

1. 新下一批素材，**先逐帧标注，标的时候不看程序的结果**；
2. 第一次跑的结果，才是当时规则的**独立准确率**；
3. 之后可以看错误、改规则，但这批就不再算留出集，文档里的数字注明"有偏"。

颠球前后做了 5 批、运球 5 批、跳绳 2 批。最可信的是每个项目最后一批第一次跑的数字（颠球 86.7% / 86.7%、跳绳 99.6% / 98.4%、运球 97.9% / 100%）。

### 1.4 改了不能变差

- 每次改规则，**所有标注集重跑一遍**，变了的地方逐个看；新数到的触地、触球逐个回看视频确认是真的；
- 每个修掉的问题，尽量在 `tests/` 里加一条用合成轨迹或关键点复现它的回归测试（不依赖视频，CI 里跑）；
- 只为提速的改动，要求结果**完全不变**：轨迹 JSON 逐项相同、成片逐帧像素 MD5 相同；
- 改了运球、跳绳的代码，要核对颠球的分析和成片逐字节不变。

### 1.5 还缺什么

所有素材都是图库视频（专业拍摄、以大人为主），**没有用户手机实拍的视频**。真实场景（孩子、家长手持拍、操场上有别人）的准确率还要实拍一批来测。

## 2. 通用的取舍

| 取舍 | 选了 | 理由 |
|---|---|---|
| 训练模型 vs 手写规则 | 规则 + 预训练检测和关键点 | 没有标注数据也能起步；每个错误能定位到一条规则、改起来有针对性。代价是容易照着看过的视频过拟合，所以有上面那套留出集的规矩 |
| 阈值用像素 vs 物理单位 | 物理单位（球半径、身高、秒、重力） | 近景、远景、横屏、竖屏、慢动作用同一套阈值 |
| 漏数 vs 多数 | 看项目：颠球宁可少断一次连击；运球宁可漏数不多数 | 颠球里"明明没落地却重新计数"一眼就看得出来，比少断一次难受得多；运球只看得见一侧的触地，强行算上容易多数 |
| 整段离线 vs 边分析边渲染 | 整段离线 | 试过用前一部分视频先算：落后 3 秒的检查点只有 55% 和整段算的完全一致。选轨迹、球的大小、重力比例尺、跳绳的节奏都要看整段 |
| 提速：结果变 vs 不变 | 优先做结果不变的 | 结果变了就要重跑全部评估、重新确认准确率；TensorRT FP16、GPU 画特效这类会改结果的放到最后 |
| 精度 vs 速度 | 看边际收益 | 颠球检测：换大模型 YOLOX-m 慢一倍还更差，没换；"每帧都放大复检"比"不确定才放大"只多 1 个百分点召回、慢 33%，选了后者 |

## 3. 颠球

### 3.1 演进

| 阶段 | 改了什么 | 结果 |
|---|---|---|
| 原型 | YOLOX-s 逐帧检测 + 全片最优路径选球 + 分段拟合抛物线找触球 | 4 段 53 次触球全对（规则就是在这 4 段上调的） |
| 第 1 批留出集，第一次跑 | — | **74.8% / 93.9%** |
| 修横屏地面线 | 地面线按真实画面算 | 76.2% / 94.0% |
| 加人体关键点 | 地面线 = 脚底；手接不算；触球部位 | 第 2 批第一次跑：不用关键点 80.3% / 94.0% → 用关键点 **94.9% / 94.1%** |
| 离人 2 米外的弹跳不算 | | 第 2 批 94.9% / 96.5% |
| 第 3 批第一次跑 | — | **97.0% / 73.6%**（误报全在"地上玩球、头上平衡"的视频里） |
| 地上玩球、头上平衡、更宽的手接 | 贴地时间占比、头颈托着走 | 第 3 批 97.0% / 87.7%；真颠球的 6 段 59/61、0 误报 |
| 第 4 批第一次跑 | — | **93.6% / 83.9%** |
| 球没碰到人、从地上挑起 | `far_*`、`rest_*` 两条规则 + 复查改 4 处标注 | 前四批合计 96.6% / 94.5% → 96.1% / 97.0% |
| 第 5 批第一次跑 | — | **86.7% / 86.7%**（独立） |
| 前后没人不算、人附近定比例尺 | | 第 5 批 86.7% / 89.7% |
| 人周围放大复检 | 见 3.7 | 第 5 批 **91.7% / 88.7%**；前四批 96.3% / 96.6% |

每一批第一次跑都比上一批调完以后低（74.8% → 94.9% → 97.0% → 93.6% → 86.7%），说明每批调完的数字都偏乐观；第 5 批的素材也明显更难（剪影、多镜头、手上动作多）。

### 3.2 选错球

- **问题**：场边放着第二个球、地上的球、白色的鞋，检测器都会报成 `sports ball`。
- **方案**：不逐帧挑分最高的，而是把全片的候选连成有向无环图，求得分最高的一条路径；静止不动的候选不给分，超过物理速度上限、尺寸突变的不连。
- **还有的问题**：选路径不看离人远近。第 4 批有一段后面地上有个慢慢滚的球，路径跟过去了（漏 3 次）。要改是大改，没动。

### 3.3 停球、贴地触球被当成落地

- **现象**：最早 4 段里，一段 25 次触球的视频被拆成 8、2、9、2、2 五组。放大看，4 次"落地"里只有 2 次是真的：一次球停在脚背上半秒再挑起，
  一次是贴着地面用脚碰了一下。另一段球落在脚尖上、沿小腿弹回大腿高度，也被当成落地。
- **原因**：
  - 拟合的抛物线把停球那几帧当离群点，一路外推到了地面；
  - 球在脚前面、离镜头更近时，画面里和鞋底一样低。
- **方案**：判断落地只用真检测到的位置，不用外推；再加一条物理判据：球没有明显低于地面线、弹回不低于落下高度的 85%，就是脚给了力
  （球自己落地只能弹回 25%–70%）。
- **效果**：变成 8、2、15 三组，和复查后的标注一致。
- **取舍**：球先碰一下地、紧接着被脚铲起，只看轨迹分不清，现在按脚触球算，不断连击。误拆连击用户一眼就看得出，比少断一次难受。

### 3.4 横屏视频的地面线

- **现象**：第 1 批第一次跑只有 74.8%，横屏素材的低位触球几乎都被当成落地。
- **原因**：横屏视频放进竖版画布后上下是模糊垫底，人的脚被真实画面的下边缘截断，程序把这条边当成了地面。
- **方案**：地面线按真实画面算。修完 74.8% → 76.2%，剩下的漏数主要是下一条。

### 3.5 只看轨迹分不清落地和低位触球

- **现象**：低机位、只拍脚的近景里，球在脚前面、离镜头近，看起来比脚还低；日落剪影那段 22 次只数对 5 次。手臂上滚的球、手抛接被当成触球。
- **方案对比**（第 2 批，第一次跑）：

  | | 召回 | 精确率 | 代价 |
  |---|---|---|---|
  | 只看球的轨迹和人框 | 80.3% | 94.0% | — |
  | 加 RTMPose 关键点 | **94.9%** | 94.1% | 本机每 30 秒视频分析多约 12 秒 |

- **关键点用来做什么**：地面线 = 支撑脚的脚底（近景、仰拍、截断都不受影响）；球贴着前臂、脚和膝都不在附近是手；触点离哪个部位最近。
- **选择**：加。12 秒的代价换 14 个百分点的召回。

### 3.6 地上玩球、头上平衡

- **现象**：第 3 批第一次跑 97.0% / 73.6%，误报全部出在没在颠球的视频里：在地上拨球带球、把球顶在头上平衡、颈后停球。
- **方案**：
  - 触点前后 0.5 秒里球有 40% 以上的时间贴着地面，是在地上玩（真触球最多 35%）；
  - 触点在头胸附近、之后 0.4 秒里球相对颈肩几乎不动（< 0.75 个球半径；颠起来的球 ≥ 0.9，多数 ≥ 1.7），是托着走；
  - 头上平衡、停球不计数，**也不断连击**（球没落地、没用手）。
- **效果**：97.0% / 87.7%；6 段真颠球 61 次数到 59 次、0 误报，剩下的误报都在"地上拨球"的视频里。

### 3.7 落地反弹和低位触球

- **现象**：第 4 批第一次跑 93.6% / 83.9%。误报主要是：球在镜头前落地、射门撞网、地上滚的球磕一下；从地上把球挑起来。
- **方案**：
  - **球没碰到人**：看得见脚，而脚、大腿、头、胸离球都在 2.5 个球半径以外，并且是被动反弹（弹起不到落下的 75%），判成落地；
  - **从地上挑起**：触点前球几乎没在下落（不到半个球半径），球底离地面不到 1 个球半径，不算触球。
- **效果**：四批合计误报 23 → 12 次，漏检 14 → 16 次（多漏的 2 次是关键点认错了人或部位）。精确率涨得多、召回略降，接受。
- **事后检验**：在之后才下载的第 5 批上，这两条让误报从 10 次降到 8 次，召回不变，说明不是只对第 4 批有效。

### 3.8 检测不到球：剪影、小球

- **现象**：第 5 批漏的 8 次多数是**没检测到球**：日落剪影里球是一团黑影，检测分只有 0.1 上下，触球前后几十帧都没检出。
- **原因**：竖版画布整帧缩到 640×640 时缩小 3 倍，球只剩 10–20 像素。
- **方案对比**（在第 4 批上比，选定以后才跑第 5 批）：

  | 方案 | 召回 / 精确率 | 每帧（GTX 1050 Ti） |
  |---|---|---|
  | 原来：整帧检测 | 92.4% / 93.6% | 85 ms |
  | 每帧都在人周围裁一块放大，再检一次球 | 93.7% / 92.5% | 128 ms |
  | 换更大的 YOLOX-m | 89.9% / 92.2% | 177 ms |
  | **整帧检测在人周围已经有把握（分数 ≥ 0.5）就跳过，否则放大再检** | 92.4% / 93.6% | 96 ms |

- **选择**：最后一种。它在第 4 批上和原来一样（第 4 批没有剪影这类问题），但能救回检测不到的情况，只慢 13%；每帧都放大召回只高 1 个点、慢 33%；
  大模型又慢又差。
- **效果**：第 5 批 86.7% / 89.7% → **91.7% / 88.7%**，剪影那段漏的 3 次全找回来；前四批基本不变。
- **副作用和补救**：放大后会检出远处的小东西（地上别的小球、反光）。一段运球视频因此冒出 74 个半径 8 像素的假球，把球的参考大小拉成 8.6，一下都没数到。
  加了过滤：半径不到 0.25 × 0.065 × 人高的不要，颠球结果不变，运球恢复。

### 3.9 出片门槛

- **问题**：42 段测试素材里，6 段"在地上玩球"的视频会被误数出 1–2 个。
- **方案对比**：最长连击 ≥ 3 才出片能全部挡掉（真颠球的 29 段最长连击都 ≥ 3），但也会挡掉只会颠一两个的新手。
- **选择**：颠到 1 个就出片（`MIN_COMBO = 1`），新手体验优先；常量留着，可以按需要提高。

## 4. 跳绳

### 4.1 演进

| 阶段 | 改了什么 | 结果 |
|---|---|---|
| 原型 | 髋部波峰 + 两脚都离地；节奏按本段视频估；垫步按大小去掉 | 6 段 73 跳全对（4 段调规则 + 2 段规则定好后才标） |
| 换一台机器跑关键点 | 垫步改按节拍判断 | 两台机器都是 73/73 |
| 慢动作、摇绳节奏核对、多人选人、遮挡 | | 第 1 批不变，没标注的视频上几处变化逐个核对 |
| 第 2 批第一次跑 | — | **484 跳 99.6% / 98.4%**，28 段里 26 段计数完全对 |
| 一圈跳两下 | 按摇绳相位挑出过绳的那一下 | 第 2 批 99.6% / 99.8%（有偏：做这个功能时看过那段） |

### 4.2 只看人，不看绳子

- **问题**：30 帧的视频里，正常速度的绳子每圈只在一两帧里有一道淡弧线。
- **试过**：脚附近取一条横带，和前后几帧的中位数相减，数"像细线一样在动"的列。粗彩绳、转得慢、固定机位时，波峰能对上过绳时刻（也有误报）；
  普通细绳、手持拍时完全淹没在镜头晃动和地面纹理里。
- **选择**：计数靠人体关键点，绳子只从手腕的摇绳节奏间接看。代价是"空跳（不拿绳）、绊绳"看不出来。

### 4.3 垫步：按大小还是按节拍

- **问题**：两跳之间的小颠动、垫步也是髋部的一个小波峰。最初的规则是"不到相邻候选 35% 的不算"。
  换一台机器（云端 V100）重跑关键点，数值有细微差别，一段视频里一个垫步的比例是 0.353，卡在门槛边上翻成了一跳。
- **为什么不能只调门槛**：没标注的视频里，有在节拍上、只是跳得低的真跳（逐帧看过脚确实离地），只有相邻的 0.36–0.45，门槛提高会把它们去掉。
- **方案**：改成按节拍判断：小候选离相邻候选只有半拍左右（垫步约 0.3 拍，门槛 0.65 拍）是垫步；一侧两拍多内没有大跳的是起跳前、停下后的小动作；
  两边隔一拍左右都有大跳的是真跳。
- **效果**：两台机器的关键点都是 73/73、0 误报，离门槛也有余量。

### 4.4 慢动作

- **问题**：图库素材里慢动作很多，跳速、用时按视频时间算会偏低。
- **方案**：腾空段髋部是加速度为 g 的抛物线，按假定身高 1.65 m 换成米，量出"视在重力"。正常速度 8–11 m/s²，2 倍慢放约 2.5，4 倍约 0.6；
  低于 6.5 当慢动作，按 √(9.8/g) 换回真实时间。不依赖视频元数据（很多慢动作素材的元数据就是普通的 25/30 帧）。

### 4.5 数成两倍或一半

- **检查**：绳子每过脚一次手腕转一圈。`arm_sync` 是手腕在"一跳的间隔"上的自相关：数对了接近 1，数成两倍是负的。能看清手的视频在 0.5–0.9；
  剪影、多人、镜头摇的接近 0，只给提示。
- **跑步跳**（左右脚交替、每步都过绳）：一步大一步小，小的单脚着地，会被去掉一半。手腕节奏清楚、髋部每圈都起伏、却只数到一半时，
  改成"一只脚离地就算"重数，节奏对上摇绳才用。一段视频 4 → 9 跳。
- **一圈跳两下**（初学者、小孩：绳子在头顶时垫一下，过绳时再跳一下，两下一样高）：跳的间隔只有摇绳周期的 0.4–0.62 倍时触发。
  33 段标注视频里人跳到最高的那一刻都在摇绳周期的 0.5–0.6 处，留离 0.55 近的那簇。一段视频 15 → 8 跳；其余 113 段一次都没触发。
  只有 1 个真实例子，能力还要打折看。

### 4.6 多人入镜

- **问题**：原来只跟画面里最大的人。有的视频离镜头最近的是背对镜头站着的人（0 跳），有的是画面边上只露出腿的人。
- **方案**：每个人都跑关键点，按人框重叠和衣服颜色连成轨迹，每条轨迹单独计数；跳数只当门槛（≥ 3 且 ≥ 最多那条的 40%），够格的里面挑"离镜头近 × 在画面里时间长"的。
- **为什么跳数不直接比大小**：后面的人被前面的人挡着，脚点少，常数少；拍视频的人想拍的多半是离镜头最近、在跳的那个。

### 4.7 遮挡和关键点出错

- **方案**：漏一跳时按节拍补回；人短暂不在画面里不算断绳，空档后的跳落在节拍上时补上看不见的跳；髋部关键点跳变时，用彼此一致的肩膀和头替换（只换 ≤ 0.2 秒）。
- **试过但没用**：直接取髋、肩、头三处的中位数，压力测试更好，但真实视频里低头看绳、走近镜头时头和肩膀自己在动，会多数、丢最后一跳。
- **压力测试**（在标注视频的关键点上随机挖掉 30% 时间）：

  | 遮挡 | 改前 | 改后 |
  |---|---|---|
  | 脚和脚踝丢了 | 98.4% / 97.8% | 99.5% / 96.5% |
  | 整个人没检测到（看得见的跳） | 59.5%（85.2%）/ 97.2% | 77.4%（93.5%）/ 95.2% |
  | 髋部、肩膀或头乱跳 | 95.0% / 93.5% | 100% / 100% |

### 4.8 双摇和双人 PK

- **双摇**：数一次腾空里手腕到最高点几次。手腕关键点会抖，所以加了四道门槛，每道都有量出来的依据：真实腾空 ≥ 0.27 秒、每圈手腕抬起 ≥ 2% 身高
  （真双摇 2.3% 以上，抖出来的 0.1%–1.4%）、脚离地 ≤ 30% 身高（跳大绳时收腿高跳、手随跳甩动）、整段有摇绳节奏。74 段里判出多摇的 4 段都逐跳看过（3 段确认是双摇，1 段的一下绳子看不清、可能对）。
- **PK 领先要领先 2 个才算**：两人差不多同时跳时，谁先落地谁就"领先 1 个"，一场 43 比 42 的比赛按领先 1 个算"反超"了 6 次。
- **慢放倍数两人共用**：各算各的会不一样，同一段视频两人的跳速就没法比。

## 5. 篮球运球

### 5.1 演进

| 阶段 | 改了什么 | 调参集 | 验证集 | 第 4 批 |
|---|---|---|---|---|
| 原型（触地 = V 形急转的最低点） | | 97.7% / 100% | 第一次跑 **75.3% / 100%** | |
| 底边切掉的球、只拍到腿、近处的大球 | 见 5.3 | | 89.0% / 100%（有偏） | |
| 暗光：门槛按局部球大小、慢的一边够一半、短组的节奏 | 见 5.4 | 98.0% / 100% | 90.4% / 100% | 第一次跑 **72.2% / 96.3%** → 83.3% / 96.8% |
| 触地在画面底边外、分组下限 0.8 → 1.8 秒 | 见 5.5 | 98.0% / 100% | 91.8% / 100% | 88.9% / 97.0% |
| 两下也算一组 | | | 97.3% | 不变 |
| 第 5 批第一次跑 | — | | | **第 5 批 97.9% / 100%（独立）** |

运球的误差几乎全是漏数，多数极少：每次改动后新数到的触地都逐个回看，都是真触地。

### 5.2 不用颠球的抛物线平滑

运球时手在往下推球，触地是 V 形尖角，不是自由落体。颠球的分段抛物线会把尖角磨圆、把触地时刻挪开，所以运球直接用选中的原始检测，
短漏检线性补上。触地判据是"局部最低点 + 两边都快"：手在上面接球是慢慢减速，不算。

### 5.3 验证集第一次漏了四分之一

- **原因**都在找球上：
  - 横屏素材里，球碰地的那一下被真实画面的底边切掉，检测框只框到露出来的半截；
  - 只拍到腿时，球每一下都升到画面外，选轨迹时把前面一段丢了；
  - 球离镜头近，比按人框估的大很多，被当成尺寸不对扣分。
- **方案**：底边切掉时按球的上沿加附近帧的正常半径修正球心；长时间没球时跳过的代价调低；运球时不按大小扣分（只去掉小很多的）。
- **效果**：75.3% → 89.0%。这是按验证集的漏数改的，所以之后又标了第 3 批（3 段，改完后第一次跑 100% / 100%）。

### 5.4 暗光片段

- **先排除检测问题**：把画面提亮（gamma、CLAHE）再检测，检出球的帧数几乎不变（83 → 83 帧）。漏检的帧里球确实不在光里、被腿挡住或出了画面。
  所以**没有加提亮预处理**，问题在判定门槛上。
- **原因**：那几下球离镜头远（或暗处只框到亮的半截），看起来只有整段中位数的八成多，速度、弹起高度按整段的球大小算，刚好卡在门槛下；
  斜着拍的竖直方向只有一边快；暗处漏掉几下后间隔忽长忽短，按头一个间隔定节奏就断开了。
- **方案**：门槛按这一刻附近的球半径算；V 字快的一边够门槛、慢的一边够一半；一组不到 3 个间隔时节奏取它和整段节奏里大的。
- **没做的**：只在触地一侧看得见球的几下（从暗处直接落到地上、触地后进了暗处）。只靠一侧没法确认是一次运球，强行算上容易多数，宁可漏。

### 5.5 触地在画面底边外

一段视频漏的几下，原因是四个问题叠在一起：

- **重复帧**：24/25 帧的视频转成 30 帧，每 4–5 帧重复一帧，重复帧夹在触地前面时，那一边的速度量出来几乎是 0。
  重复帧能认出来（人框、关键点和上一帧逐位相同，个数和帧率换算对得上），先去掉、在原视频的帧上数，再换回帧号。105 段里 59 段有重复帧；
- **球在最低处停一两帧**：量速度时跳过平底；
- **弹起高度**：按两段直线的交点（触地点）算，不按看得见的最低点；
- **低分检测被扔**：球糊了、半个出画面时分数只有 0.1–0.2，选轨迹时低分扣分从 −0.25 调到 −0.15（−0.15 到 −0.05 结果一样，取了最保守的）。

**分组**：核对全部 105 段时发现，坐轮椅运球的一段节奏慢（1.4–1.5 秒一下），被当成中途停下拆开扔掉。标注过的片段里连续运球的间隔最长 1.6 秒，
拿着球停下来至少 2.1 秒，所以断开的下限从 0.8 秒改成 1.8 秒，落在两者之间。

### 5.6 一组至少几下

原来停下以后至少要连续 3 下才算一组，验证集里有 4 下真触地因此不算。改成 2 下（只有 1 下的仍不算），验证集 91.8% → 97.3%，
105 段里多数到的 30 下逐个看过都是真触地。

### 5.7 动作：交叉还是胯下

- **思路**：胯下时球从两腿之间穿过，从镜头看有一段在小腿后面：检测不到，或检测框突然变小。交叉时球一直在腿前面。
  触地点在两脚连线前面多远也有关系，但机位低时差别被压扁，只当参考。
- **验证集第一次跑** 30/36；复查发现最初的标注把 2 下胯下标成了交叉、1 下其实看不清，按改正后的标注是 32/35。
- **按验证集改的一处**：球触地时出了画面边，被当成躲在腿后面。加了"贴着画面边不算被腿挡"之后 34/35，这个数字有偏。
- **只在面对镜头时判**：背对、侧身时左右手对不上、腿挡球的关系也反过来，不判比判错好。

### 5.8 背后运球

- **问题**：球从一侧髋部躲到身后、从另一侧出来，触地常常也在身后，按 V 形找触地根本找不到这一下。
- **方案**：另找一段 3 帧到 0.8 秒的连续漏检，进去前在一侧快速往下、出来后在另一侧往上，进出都在髋到膝的高度，球不比两髋宽太多（离镜头近的球藏不到身后），
  不贴画面边。只在面对镜头时找：背对镜头时球在身前被身体挡住也是这个样子。
- **验证**：为了找例子又下了 54 段，两批 105 段里真实的背后运球只有 1 下，判对了，别处没有误判。1 个例子说明不了准确率，要专门拍。

## 6. 成片特效

### 6.1 真实视频上看不清、特效太大

最初的特效参数是在暗色合成场景里调的，放到真实视频上出了几个问题，先量了再改：

| 问题 | 量出来的 | 改法 |
|---|---|---|
| 亮背景上看不清字 | 4 段素材里 3 段，计数区域背景亮度 0.33–0.62，高亮度彩色数字对比度只有 1.15–2.04（大字至少要 3，小字 4.5）；换成白字也只有 1.57–2.78 | 文字改白色；文字下面垫保护层；分析时统计画面亮度，按背后亮度决定压暗多少；单帧预览直接量出每行字的实测对比度 |
| 特效太大 | 球在真实视频里占屏宽 12%–19%（按 7% 设计的），按球的大小放大后，触球光环最大直径占屏宽 56%–89%，像个靶子 | 跟球走的效果按球缩放，但以屏宽设上下限：冲击波最大不超过屏宽 14% |
| 拖尾是一团光斑 | 真实的低颠在 0.36 秒内只走 0.6–1.0 个球径，固定时长的拖尾又和球一样粗 | 拖尾按移动距离截取（最长 6 个球径），球几乎不动时淡出 |

**保护层的取舍**：比过几种（`still.mjs` 并排画同一帧，标出实测对比度）：按亮度自适应的暗色底板（`plates`）、上下渐进模糊（`edges`）、
整页降饱和压暗（`veil`）、两者混合（`mix`）、上下很淡的渐变 + 文字自带阴影（`light`）。压得越重字越清楚，但原片颜色和清晰度损失越大，
而原片好看是用户愿意分享的前提。默认用 `light`，对比度按文字笔画周边的背景量；其余几种留作选项。

### 6.2 被短视频 App 的界面挡住

成片多半会发到竖屏短视频 App 里，推荐页上顶部栏、右侧点赞栏、左下胶囊和文案会盖住画面。按一台手机的截图量出这些区域（`SAFE_AREA`），
做了把数据面板抬高、右边收窄的布局（`v3s`、`v3l`），单帧预览可以把遮挡区画成红色检查。默认布局（`v3`）不管遮挡、面板贴底，少挡人；两种按需选。

### 6.3 多线程渲染结果不一致

- **现象**：同一帧用不同线程数渲染，30 秒视频里 331 帧有差别（最大差 21 个灰阶）。
- **原因**：拖尾泛光图层、抠球的小画布只清空了局部，放大贴回时插值会读到之前画过的帧留下的像素，结果取决于这个线程之前画过哪一帧。
- **方案**：整块清空。现在任何线程数结果逐字节相同，这也是后面所有"逐帧 MD5 核对"的前提。

## 7. 速度

### 7.1 瓶颈在 CPU

云端 V100 实测 GPU 平均只用了 17%–24%：每条 30 秒视频约 240 核·秒，大头是 x264 编码（约 60）、分析（约 70，含解码和推理前后处理）、
画特效（约 50）、解码（约 15）。所以**换更贵的 GPU 没用**，部署应该选 CPU 核数多、GPU 普通的机器。

### 7.2 软件上能做的

| 做法 | 每条省 CPU | 结果变不变 | 工作量 | 选择 |
|---|---|---|---|---|
| 分析三级流水线（解码、推理、关键点各一个线程） | — | 不变 | 小 | **做了**：第 1 遍 25.6 → 15.0 s |
| 检测预处理和输出筛选挪进模型图在 GPU 做 | 约 3% | 不变（逐位核对） | 1–2 天 | **做了**：检测每帧 13.0 → 9.2 ms |
| 渲染线程自己转 YUV、C 原生像素模块、少拷贝 | 每帧约 20 ms | 不变 | 小 | **做了** |
| 只解码一次（解码帧存内存盘给渲染） | 约 8 核·秒 | 不变 | 中 | **做了**（4K 源例外，缓存反而更慢） |
| 编码改 `superfast` | 约 15 核·秒 | 文件大 34% | 改参数 | 没做：只快 2 秒 |
| 关键点只在触球点附近跑 | 约 10 核·秒 | **计数会变** | 2–3 天 | 没做：要重跑全部评估 |
| 特效改用 GPU 画 | 约 20% | 像素有细微差别 | 2–3 周 | 没做：风险大 |
| Python 主循环用 C++ / Rust 重写 | 约 2% | 要逐帧核对 | 1–2 周 | 没做：真正耗时的部分（x264、FFmpeg、Skia、ONNX Runtime、OpenCV）本来就是 C/C++ |
| 边分析边渲染 | 用户等待少一半 | **计数会变** | 中 | 没做：见第 2 节 |

硬件上打开 GPU 编码（NVENC）一项就能省约 60 核·秒，比上面软件改动加起来都多。

### 7.3 GPU 编码的画质

最初用的 NVENC 参数（`p4`、`cq 21`）文件是 x264 的 1.8 倍。按 VMAF 调参（30 秒颠球样片，对未压缩的成片帧）：

| | 大小 | VMAF | 最差 1% 帧 |
|---|---|---|---|
| libx264 `veryfast` `crf 20` | 31.4 MB | 95.7 | 93.1 |
| NVENC `p4` `cq 21` | 55.8 MB | 99.1 | — |
| **NVENC `p5` `cq 27` lookahead 20、B 帧 3** | **28.8 MB** | **96.5** | 93.6 |

选了最后一行：比 x264 小、画质略好，编码快 1.7 倍；`cq 21` 的画质高出看不出来的一截，文件却大近一倍。

### 7.4 环境踩过的坑

- pip 默认装的 CUDA / cuDNN 比驱动支持的新：模型能加载，一推理就报 `CUDNN_STATUS_EXECUTION_FAILED_CUDART`。按驱动版本固定库的版本。
- Windows 上找不到 CUDA DLL 时 onnxruntime 会**悄悄退回 CPU**，慢 2.5 倍左右，所以加了 `COMBOCAM_CUDA_DLL_DIR`，日志里写明用的是哪个设备。
- 老显卡的驱动装不到新版 FFmpeg 的 NVENC 要求的版本，加了 `COMBOCAM_FFMPEG_ENC` 只换编码用的 FFmpeg。
- 只用 CPU 跑 YOLOX-s 每帧约 0.76 秒，30 秒视频要 11 分钟以上，所以文档里明确建议用 GPU。
